CI/CD를 배우는 이유
프로그램을 수정한 뒤 개발자의 PC에서만 잘 작동한다고 해서 사용자가 보는 서비스까지 안전하게 바뀐 것은 아닙니다. 변경한 코드를 저장소에 올리고, 자동 검사를 통과시키고, 배포된 URL에서 다시 확인하는 흐름이 필요합니다. CI/CD는 이런 반복 작업을 일관된 순서로 처리하는 데 도움을 줍니다. 우리 수업의 챗봇도 Python 서버와 React 화면을 수정한 뒤 GitHub와 Vercel을 거쳐 사용자에게 전달됩니다.

CI와 CD의 의미
CI는 지속적 통합을 뜻합니다. 여러 사람이 만든 변경을 자주 합치고, 새 코드가 기존 기능을 망가뜨리지 않았는지 자동 빌드와 테스트로 확인하는 방식입니다. CD는 문맥에 따라 지속적 전달 또는 지속적 배포를 뜻합니다. 전달은 배포 가능한 상태까지 자동으로 준비하고, 배포는 검사를 통과한 변경을 실제 서비스에 반영하는 데 초점을 둡니다. 두 용어를 외우는 것보다 코드 변경이 어느 단계에서 검증되고 공개되는지 구분하는 일이 중요합니다.

버전 관리와 원격 저장소
Git은 코드의 변경 이력을 커밋으로 기록합니다. 커밋은 현재 작업의 의미 있는 상태를 로컬 저장소에 남깁니다. git push는 그 커밋을 GitHub 같은 원격 저장소로 보냅니다. 원격 저장소에 다른 커밋이 먼저 들어왔다면 push가 거절될 수 있습니다. 이때는 상태와 변경 이력을 확인하고 원격 변경을 가져와 충돌을 해결해야 합니다. 강제로 푸시해 다른 사람의 이력을 덮어쓰는 방법은 공동 작업 수업에서 적절하지 않습니다.

파이프라인과 자동화의 시작점
파이프라인은 코드가 검사와 배포를 거치는 작업 순서입니다. GitHub Actions에서는 저장소에 push가 일어났을 때 작업을 시작하도록 설정할 수 있습니다. pull request가 열리거나, 정해진 시각이 되거나, 사용자가 직접 실행할 때 시작하는 방식도 있습니다. 어떤 사건이 작업을 시작하는지 정하는 부분을 트리거라고 부릅니다. 수업에서는 main 브랜치에 새 커밋을 push했을 때 배포가 시작되는 흐름을 관찰할 수 있습니다.

워크플로, 작업, 단계
GitHub Actions의 워크플로는 자동화 전체를 정의한 파일입니다. 워크플로 안에는 하나 이상의 job이 있고, 각 job은 여러 step으로 구성됩니다. 예를 들어 첫 단계에서 소스 코드를 가져오고, 다음 단계에서 필요한 패키지를 설치하고, 마지막 단계에서 테스트를 실행할 수 있습니다. job은 GitHub가 제공하는 runner 또는 직접 운영하는 runner에서 실행됩니다. 실패가 나면 전체가 실패했다는 표시만 볼 것이 아니라 어느 단계에서 어떤 오류가 났는지 로그를 확인합니다.

자동 테스트의 역할
테스트는 예상한 입력에 대해 프로그램이 예상한 결과를 내는지 확인합니다. 예를 들어 문서 검색 함수에 'chmod 권한'을 넣었을 때 Linux 자료가 선택되고, 자료에 없는 '오늘 날씨'에는 빈 결과가 나오는지 확인할 수 있습니다. API 테스트에서는 JSON 질문을 보내 답변과 참고 파일명 필드가 있는지 살펴봅니다. 테스트가 통과해도 모든 상황이 검증된 것은 아니므로 실제 브라우저에서 사용 흐름을 확인해야 합니다.

빌드와 배포
React 프로젝트의 빌드는 작성한 소스 파일을 브라우저가 서비스에서 사용할 결과물로 만드는 과정입니다. Python API는 서버에서 요청을 받아 실행됩니다. Vercel 같은 배포 플랫폼은 GitHub 저장소의 새 커밋을 가져와 설정에 따라 빌드하고 서비스를 갱신할 수 있습니다. 배포가 성공했다고 표시되어도 실제 URL에서 질문을 입력해 화면과 API가 함께 작동하는지 확인해야 합니다. 로컬 개발 서버에서만 동작하는 설정이 배포 환경에는 없을 수도 있기 때문입니다.

환경변수와 비밀 정보
API 키는 모델 서비스를 호출할 수 있는 권한을 가진 비밀 정보입니다. .env 파일을 GitHub에 올리지 않고, 배포 플랫폼에는 환경변수로 등록합니다. 자동화 작업에 비밀값이 필요하다면 GitHub Actions의 secret 같은 기능을 사용합니다. 화면에 보이는 React 코드에 비밀 키를 넣으면 사용자가 확인할 수 있으므로 서버에서만 읽도록 구성합니다. 로그나 오류 메시지에 키가 출력되지 않도록 하는 것도 중요합니다.

배포 실패와 되돌리기
배포가 실패하면 어떤 커밋에서 어떤 작업이 실패했는지 먼저 확인합니다. 패키지 설치 실패인지, 코드 빌드 실패인지, API 서버 실행 오류인지에 따라 조치가 달라집니다. 새 버전이 배포됐지만 기능에 문제가 생겼다면 이전 정상 버전으로 되돌릴 수 있는 방법도 운영 과정에 필요합니다. 문제를 고친 뒤에는 새 커밋을 올리고 다시 배포 URL에서 확인합니다. 실패 기록을 남기면 다음 변경에서 같은 문제를 줄이는 데 도움이 됩니다.

수업용 챗봇의 실제 흐름
학생이 자료 파일과 Python 검색 함수를 수정합니다. 로컬에서 'git commit', 'chmod 권한', 'CI/CD 파이프라인', '오늘 날씨' 질문을 시험합니다. git status로 API 키 파일이 포함되지 않았는지 확인하고 변경을 커밋한 뒤 GitHub로 push합니다. 연결된 Vercel 프로젝트에서 새 배포 상태를 확인하고 공개 URL에서 같은 질문을 다시 시험합니다. 이 순서가 수업에서 직접 경험하는 작은 CI/CD 흐름입니다. GitHub Actions 워크플로를 별도로 만들지 않아도 변경, 검증, 배포의 관계를 이해할 수 있습니다.
