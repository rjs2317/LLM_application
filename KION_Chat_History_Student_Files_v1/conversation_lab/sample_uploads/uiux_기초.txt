UI와 UX 기초: 문서 질문 챗봇을 예로 이해하기

1. UI와 UX는 무엇인가
UI(User Interface, 사용자 인터페이스)는 사용자가 프로그램과 만나는 구체적인 화면 요소다. 버튼, 입력창, 파일 선택창, 문서 목록, 대화 말풍선, 색상, 글꼴, 오류 메시지가 UI에 속한다. 예를 들어 문서 질문 챗봇의 왼쪽에 있는 ‘TXT 파일 선택’ 버튼과 오른쪽의 질문 입력창은 UI다. UI를 설계할 때는 사용자가 무엇을 누를 수 있는지, 현재 무엇이 선택됐는지, 다음 행동이 무엇인지 화면만 보고 알아볼 수 있어야 한다.

UX(User Experience, 사용자 경험)는 사용자가 목표를 이루는 전체 과정에서 겪는 경험이다. 사용자가 문서를 고르고 업로드한 뒤 목록에서 확인하고, 질문을 입력해 근거가 있는 답을 받기까지의 흐름이 UX다. 같은 기능을 제공해도 업로드 중 상태가 표시되지 않거나 결과가 늦게 나타나면 사용자는 프로그램이 멈췄다고 생각할 수 있다. 보기 좋은 화면만으로 좋은 UX가 완성되지는 않는다. 예상한 결과가 일관되게 나타나고 실패했을 때도 다음 행동을 알 수 있어야 한다.

2. 문서 업로드 흐름을 설계하기
사용자는 먼저 UTF-8로 저장된 TXT 파일을 선택한다. 프로그램은 파일 확장자와 크기를 검사한 후 서버에 전송한다. 서버는 내용을 읽어 데이터베이스에 저장하고, 저장에 성공하면 문서 ID와 파일명을 돌려준다. 프론트엔드는 문서 목록을 새로고침하여 방금 올린 파일이 보이게 한다. 새로고침 후에도 파일이 목록에 남아 있다면 브라우저 화면에만 임시로 표시된 것이 아니라 데이터베이스에 저장됐음을 확인할 수 있다. 파일을 선택만 하고 ‘문서 추가’를 누르지 않았다면 서버에 전송되지 않았으므로 새로고침 후 사라지는 것이 정상이다.

업로드 버튼을 누른 뒤에는 ‘추가 중…’처럼 진행 상태를 알려 주는 편이 좋다. 같은 버튼을 여러 번 누르면 같은 파일이 중복 저장될 수 있으므로 처리 중에는 버튼을 잠시 비활성화할 수 있다. 저장이 끝났을 때는 ‘uiux_기초.txt 문서를 추가했습니다’처럼 결과를 구체적으로 보여 준다. 같은 이름의 문서가 이미 있다면 새 이름으로 바꾸거나 기존 파일을 어떻게 처리할지 사용자에게 알려 주어야 한다.

3. 좋은 오류 메시지와 접근성
‘오류가 발생했습니다’는 원인과 해결 방법을 알려 주지 못한다. ‘UTF-8 TXT 파일을 선택하세요’, ‘파일은 1 MB 이하여야 합니다’, ‘같은 이름의 문서가 있습니다’처럼 사용자가 취할 행동을 알 수 있는 문구가 낫다. 네트워크가 끊긴 경우에는 저장에 실패했다는 사실을 명확히 알리고 다시 시도할 수 있게 한다. 서버의 내부 오류 원문이나 API 키는 화면에 노출하지 않는다.

접근성은 다양한 사용자가 기능을 사용할 수 있게 만드는 기본 조건이다. 입력창에는 ‘질문’과 같은 이름표를 연결하고, 키보드만으로도 파일 선택과 질문 전송이 가능해야 한다. 색만으로 성공과 실패를 구분하지 말고 텍스트도 함께 표시한다. 글자가 배경에 묻히지 않도록 대비를 확보하고, 작은 화면에서는 문서 목록과 채팅 영역이 겹치지 않게 배치한다. 이러한 요소는 장애가 있는 사용자뿐 아니라 처음 앱을 사용하는 사람에게도 도움이 된다.

4. 자료 기반 챗봇에서 중요한 UX
자료 기반 챗봇은 일반 대화 챗봇과 달리 문서의 내용을 근거로 답해야 한다. 사용자가 ‘Git commit은 무엇인가요?’라고 물었는데 리눅스 자료를 출처로 표시하면 답변을 신뢰하기 어렵다. 답변 아래에 ‘참고자료: git_기초.txt’처럼 사용한 문서 이름을 보여 주면 사용자가 근거를 확인할 수 있다. 자료에 없는 내용을 물었을 때는 지어내기보다 ‘내 문서에서 관련 내용을 찾지 못했습니다’라고 알리는 편이 안전하다. 검색 결과가 없다는 메시지와 Gemini 연결 오류 메시지도 구분해서 표시해야 원인을 파악할 수 있다.

검색 품질 역시 UX에 영향을 준다. 자료에 단어가 있어도 검색 로직이 띄어쓰기나 표현 차이를 처리하지 못하면 관련 문단을 찾지 못할 수 있다. 이때 사용자는 파일이 저장되지 않았다고 오해할 수 있다. 개발자는 먼저 문서 목록과 DB 행을 확인하고, 다음으로 검색된 문단과 출처를 확인한 뒤, 마지막으로 LLM 응답을 확인한다. 이렇게 단계를 나누어 시험하면 화면 문제인지, 자료 검색 문제인지, LLM 호출 문제인지 구별할 수 있다.

5. 로그인과 문서 권한도 사용자 경험이다
회원가입, 로그인, 승인 대기는 각각 다른 상태다. 가입 직후 아직 승인받지 못한 사용자가 빈 채팅 화면만 보면 무엇을 기다려야 하는지 알 수 없다. ‘관리자 승인 대기 중’이라는 안내와 승인 상태 새로고침 버튼을 보여 주면 상황이 분명해진다. 승인된 사용자는 자신의 문서만 보고 추가할 수 있어야 한다. 다른 사람의 문서가 목록에 나타나거나 질문의 근거로 사용된다면 이는 보안 문제이면서 심각한 UX 문제다. 화면에서 채팅 버튼을 숨기는 것만으로는 충분하지 않다. 서버의 API가 승인 여부를 확인하고 데이터베이스의 RLS가 사용자별 문서 접근을 제한해야 한다.

실습 확인 질문
UI와 UX는 어떻게 다른가? 문서 업로드 후 목록을 갱신하는 이유는 무엇인가? 오류 메시지에 해결 방법을 넣어야 하는 이유는 무엇인가? 답변의 참고자료를 표시하면 어떤 점이 좋아지는가? 승인 대기 사용자가 직접 API를 호출할 때도 차단해야 하는 이유는 무엇인가?
